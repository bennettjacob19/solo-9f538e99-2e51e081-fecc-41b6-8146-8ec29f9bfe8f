# 虚拟盘零块回收 + 坏块备用槽修复（Flask + raw 稀疏镜像 + fallocate 打洞）

虚拟磁盘里**写成零的块仍然占着宿主盘空间**：文件系统不会因为内容全零就自动释放它。
本项目提供一个网页，预置一张存于数据卷的 raw 镜像（内含稀疏空洞、写过的零块、非零块，
物理末尾另有 **2 个备用槽**），可以：

- 模拟虚拟机按 **4 KiB 块** 读写；
- 对还在原位置的块**注入读故障**（落盘，重启仍在）：该块读请求报错；
- 经**原写入入口**给故障块写满新值：**备用槽接替原位置**，内容与映射都落盘才报
  写入成功，此后按原块号透明读写；
- 一键发起/中断零块回收，实时查看镜像文件的**逻辑容量**与**宿主实占字节数**；
- 观察回收只给“已写入且全零的整块”打洞（`fallocate(PUNCH_HOLE)`），
  **不改变盘容量、不改变任何块的读值**；回收跳过故障原位置，
  备用槽里的全零块也会打洞且**打洞后槽仍归原块号**。

## 原理与关键保证

| 机制 | 实现 |
| --- | --- |
| 跳过已有空洞 | 扫描用 `SEEK_DATA`/`SEEK_HOLE` 定位已分配数据段，整段跳过空洞（含历史已打的洞） |
| 只回收整块零 | 段内只处理 4 KiB 对齐的整块；打洞前在块锁内重新校验“仍已分配且全零”，再 `fallocate(PUNCH_HOLE\|KEEP_SIZE)` |
| 容量/读值不变 | `KEEP_SIZE` 保持文件大小；打洞区域读回仍是零，非零块完全不触碰 |
| 读写不等扫描 | 块读写与回收在同一进程内通过**每物理槽一把锁**互斥，锁只覆盖单个 4 KiB 操作，不做全局暂停 |
| 不抹新数据 | “判零 + 打洞”在块锁内原子完成；判零后到达的写入会让二次校验失败而跳过该块 |
| 中断可恢复 | 打洞定期 `fsync`；中断在块边界优雅停止。已打的洞保存在镜像文件里，重启后扫描自动跳过旧洞 |
| 故障落盘 | 故障块集合与已提交映射存于 `<镜像>.remap.json`（写临时文件 + fsync + rename + 目录 fsync 原子替换），重启后故障仍在、已提交映射沿用 |
| 修复即写入 | 故障块经原写入入口写满 4 KiB 新值时：预留空闲备用槽 → 新值写槽并 `fsync` 镜像 → 提交 块→槽 映射并落盘，**两者都落盘才报成功** |
| 槽位竞争 | 数据卷只有 2 个备用槽；预留/释放在内存锁内原子完成，两个坏块争最后一槽时最多一个修复成功；无空槽时写入失败（HTTP 507）、坏块状态保留 |
| 失败/中断回滚 | 修复失败或进程中断时未提交映射不存在：块仍报读错，预留槽（内存态）自动释放、可再次分配；已写未提交的槽内容视为垃圾，下次分配时整体覆盖 |
| 回收与坏块 | 回收跳过故障块的原位置（不读不打洞）；备用槽里的全零块照常打洞，已提交映射保持不变；修复中的预留槽跳过 |

> 说明：本项目用宿主文件系统的稀疏文件模拟虚拟磁盘，`st_blocks*512` 即宿主实占字节，
> 与真实虚拟化场景中虚拟盘文件占用宿主空间的语义一致。要求底层文件系统支持
> `fallocate` 打洞（ext4/xfs 及基于 ext4 的 overlay2、docker 命名卷均支持；
> 个别网络文件系统不支持，启动时会报错）。

## 目录结构

```
app/
  constants.py       常量（4KiB、备用槽数、SEEK_DATA/HOLE、fallocate 标志、块状态）
  disk.py            DiskImage：块读写、故障注入、备用槽修复、SEEK_DATA 扫描 + 打洞回收；create_image 预置镜像
  remap.py           RemapTable：故障块集合 + 已提交映射的原子落盘（JSON + rename）
  reclaim.py         ReclaimManager：后台线程回收、取消、进度/实占统计
  api.py             与框架无关的 API 核心（Flask 与 stdlib 入口共用）
  web.py             Flask 路由与应用工厂
  server_stdlib.py   无 Flask 时的纯标准库 WSGI 回退入口（行为与 Flask 路由一致）
  cli.py             init-image / serve 命令
  static/            前端页面（块网格、备用槽面板、回收控制、块读写、事件日志）
tests/test_disk.py   纯 stdlib 自测（24 项，含并发写入、并发修复、中断重启）
Dockerfile, docker/entrypoint.sh, docker-compose.yml, requirements.txt
```

## Docker Compose 启动（推荐）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

- 镜像文件与映射元数据固定在命名卷 `disk-data` 挂载的 `/data`（`disk.raw` 与
  `disk.raw.remap.json`），容器重建不丢盘、不丢洞、不丢故障与已提交映射；
- 环境变量 `BLOCK_COUNT`（默认 256，即 1 MiB 逻辑容量 + 2 个备用槽）可在
  `docker-compose.yml` 调整；
- 容器启动时先幂等初始化镜像（已存在且容量匹配则直接复用；旧版无备用槽布局的
  镜像会在尾部追加备用区后复用），再以 gunicorn 单进程 8 线程运行
  （回收与修复在后台/请求线程，块操作走块级锁）。

停止与清理：

```bash
docker compose down            # 保留数据卷
docker compose down -v         # 连同镜像卷一起删除（下次启动重新预置）
```

## 本地直接运行（无 Docker 时）

```bash
# 有 Flask 时
pip install -r requirements.txt
IMAGE_PATH=./data/disk.raw gunicorn --workers 1 --threads 8 'app.web:create_app()'

# 没有 Flask 也可以跑（纯标准库回退入口，API 完全相同）
IMAGE_PATH=./data/disk.raw python -m app.server_stdlib
```

## 预置镜像布局（256 块 × 4 KiB = 1 MiB 逻辑容量 + 2 备用槽）

| 区域 | 类型 | 是否占宿主空间 | 回收行为 |
| --- | --- | --- | --- |
| 块 0–63 | 稀疏空洞（`ftruncate`） | 否 | 扫描跳过 |
| 块 64–127 | 写过的全零块 | 是 | 打洞释放 |
| 块 128–191 | 非零块（含块号标记） | 是 | 判非零跳过 |
| 块 192–255 | 稀疏空洞 | 否 | 扫描跳过 |
| 备用槽 0–1 | 空洞（修复时接替坏块原位置） | 否（被占用后视内容而定） | 全零则打洞，映射保留 |

初始实占 524288 B（128 块）；完整回收后实占 262144 B（仅剩 64 个非零块），
逻辑容量始终 1048576 B，物理文件大小始终 1114112 B（含备用槽）。

## 坏块演练路径（网页）

1. 在块网格中点选一个**还在原位置**的块（未显示 `→sN` 标记），点“注入读故障”：
   该块变红，读请求报 500（模拟介质读错误），故障落盘，重启仍在；
2. 用“写非零图案 / 写全零块 / 按 Hex 写入”任一**原写入入口**写满 4 KiB 新值：
   一个空闲备用槽接替原位置，内容与映射都落盘后返回成功，块标记变为 `块号→s槽号`；
3. 此后按原块号读写，透明落到备用槽；备用槽面板实时显示槽占用与空槽数；
4. 两个备用槽都占满后，再写其他故障块返回 507，坏块状态保留；
5. 发起回收：故障原位置被跳过（计入“跳过的故障原位置”），
   备用槽里的全零块被打洞但映射保留。

## HTTP API

| 方法/路径 | 说明 |
| --- | --- |
| `GET /api/status` | 容量/实占、每块状态、回收任务进度、故障块/重映射/空槽数 |
| `GET /api/blocks/<i>` | 查看块状态、hex 全文与 ASCII 预览（故障未修复返回 500） |
| `POST /api/blocks/<i>/read` | 模拟虚拟机读（只读，不改任何状态；故障未修复返回 500） |
| `POST /api/blocks/<i>/write` | 写 4 KiB，body：`{"hex": "..."}`（必须恰好 8192 个 hex 字符）；故障块触发修复，响应带 `repaired` / `remapped_to`；无空槽返回 507 |
| `POST /api/blocks/<i>/write-pattern/zero|data` | 便捷写全零 / 非零图案（同样是修复入口） |
| `POST /api/blocks/<i>/fault` | 对还在原位置的块注入读故障（幂等；已重映射的块返回 409） |
| `POST /api/reclaim/start` | 发起回收（已在运行则返回当前状态） |
| `POST /api/reclaim/cancel` | 请求中断，当前块处理完即停，已打的洞保留 |

## 已知边界

- 打洞按 4 KiB 对齐；若数据段首尾不足 4 KiB 对齐（本项目镜像与写入都按 4 KiB 对齐，不会出现），零碎部分保留不动。
- 回收任务进度计数保存在进程内存，持久状态只依赖镜像文件与映射元数据；进程重启后进度计数归零，但盘上已回收的空间、故障标记与已提交映射真实保留。
- 修复在“内容写槽但未提交映射”时中断，槽内残留数据视为垃圾：元数据中该槽空闲，下次分配时整体覆盖，不会被任何逻辑块读到。
- 映射元数据缺失但镜像存在时，所有备用槽按空闲处理（槽内旧内容在重新分配时覆盖）；镜像重建（容量不符）时旧映射元数据一并作废。
- 当前环境未安装 Docker，compose 配置未经本机实际启动验证；核心逻辑与 HTTP 行为已通过纯标准库入口完整自测。
